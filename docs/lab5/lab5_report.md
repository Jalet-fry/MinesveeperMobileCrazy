## 1 ИНСПЕКЦИЯ ПРОЕКТА ПО ПРИЗНАКАМ ТЕХНИЧЕСКОГО ДОЛГА

В ходе аудита кода проекта «Crazy Minesweeper» был выявлен ряд архитектурных и технических проблем, классифицируемых как технический долг.

### 1.1 Непонятный / нечитабельный код

– **Глобальная системная опечатка**: во всем проекте (имена пакетов, файлов и классов) используется некорректное написание «Minesveeper» вместо «Minesweeper», что затрудняет поддержку и поиск.
– **Низкоуровневая логика в «Compression.kt»**: модуль распаковки уровней реализован через сложные битовые сдвиги и рекурсию. Полное отсутствие комментариев превращает файл в «черный ящик».
– **Засоренность «MinesweeperEngine.kt»**: в коде оставлены маркеры процесса разработки («ПИНГ-ПОНГ Раунд X»), создающие визуальный шум.

**Меры:** проведение глобального рефакторинга имен, документирование алгоритмов декомпрессии, очистка кода от меток процесса разработки.

### 1.2. Дублирующийся код

– **«LevelSettings.kt»**: поля `width/height` полностью дублируют `cols/rows`. Это избыточные данные, создающие риск рассинхронизации при обновлении настроек.
– **Спекулятивная универсальность**: в проекте описаны сложные формы соседей (`NeighborShape.kt`) и топологии поля (`Topology.kt`), но движок игнорирует их, используя жестко зашитые циклы `-1..1`. Логика обработки дублирует стандартное поведение, не используя заложенную гибкость.

**Меры:** удаление дублирующих полей в моделях данных, переход на использование универсальных шаблонов соседей в логике движка.

### 1.3. Отсутствие автоматизации (тестов, сборки, развёртывания)

– **Поверхностное тестирование**: Unit-тесты покрывают только базовые сценарии. Отсутствуют проверки на граничные значения (поле 1х1, 100% заполнение минами) и поврежденные данные.
– **Отсутствие CI**: нет системы автоматической сборки и тестирования, ошибки обнаруживаются только при ручном запуске.

**Меры:** расширение тестового покрытия для критических сценариев, настройка GitHub Actions для автоматизации сборки и прогона тестов.

### 1.4. Запутанная архитектура и лишние зависимости

– **«MinesweeperEngine.kt» (Божественный объект)**: класс нарушает принцип единственной ответственности (SRP), управляя одновременно генерацией, состоянием ячеек, таймером и правилами игры.
– **«GameEvent.kt» и «Topology.kt»**: содержат код, который никак не интегрирован в основную логику приложения («мертвый код»).

**Меры:** декомпозиция движка на специализированные модули (Generator, State, Rules), удаление неиспользуемых перечислений и классов.

### 1.5. Медленные / неэффективные средства

– **Оверхед рендеринга в «GameScreen.kt»**: отрисовка сетки через вложенные Column/Row создает дерево из 2500+ компонентов для поля 50х50. В Jetpack Compose это приводит к фризам интерфейса при масштабировании.
– **Неэффективный таймер**: обновление `currentTime` каждые 10 мс во ViewModel создает лишнюю нагрузку на процессор для счетчика, отображающего секунды.

**Меры:** переход на отрисовку сетки через Canvas, оптимизация частоты обновления таймера до 500-1000 мс.

### 1.6. Отсутствие / несоответствие технической документации

– Отсутствует файл README и спецификация формата сжатия карт. Сторонний разработчик не сможет подготовить кастомный уровень без изучения кода.

**Меры:** создание файла README с инструкцией по архитектуре и документирование формата обмена данными.

### 1.7. Дополнительно: критические ошибки в коде

– **«Compression.kt»**: блок `try-catch` подавляет ошибки. При повреждении данных создается пустое поле без уведомления игрока.
– **«StatsDialog»**: поле «Efficiency» содержит заглушку (1.0). Реальный расчет эффективности кликов не реализован.

**Меры:** реализация полноценной обработки исключений в модуле сжатия, внедрение формулы расчета эффективности на основе реально вскрытых ячеек за один клик.

## 2 ПЛАН МЕРОПРИЯТИЙ ПО УСТРАНЕНИЮ ТЕХНИЧЕСКОГО ДОЛГА

### 2.1 Мероприятия

1. **Исправление опечаток**: Глобальный рефакторинг Minesveeper -> Minesweeper. (Средний приоритет, 1 ч)
2. **Оптимизация рендеринга**: Переход на Canvas для отрисовки сетки. (Высокий приоритет, 6 ч)
3. **Декомпозиция движка**: Разделение «Божественного объекта» на модули. (Высокий приоритет, 3 ч)
4. **Интеграция Topology/Shape**: Оживление мертвого кода в движке. (Высокий приоритет, 3 ч)
5. **Исправление багов**: Расчет эффективности и обработка ошибок в Compression. (Высокий приоритет, 2 ч)
6. **Документирование**: Создание README и спецификации карт. (Средний приоритет, 2 ч)
7. **Автоматизация**: Настройка CI (GitHub Actions). (Низкий приоритет, 3 ч)

### 2.2 Оценка плана мероприятий

– **Выполнено в рамках ЛР (п. 1–5)**: устранены критические архитектурные монолиты и проблемы производительности. Объём работ: **15 человеко-часов**.
– **Оставлено в бэклог (п. 6–7)**: задачи по автоматизации и документированию.
– **Технический долг**: основной объем долга связан с архитектурным монолитом в движке и неоптимальным использованием ресурсов UI.

## 3 ВЫВОДЫ И КОРРЕКТИРОВКА ПЛАНА РАЗРАБОТКИ

### 3.1 Необходимость устранения долга: частичная и приоритизированная

– **Обязательно**: оптимизация графики (Canvas) и декомпозиция движка. Без этого добавление новых игровых режимов приведет к деградации проекта.  
– **Желательно**: исправление опечаток и оживление неиспользуемого кода топологий.

### 3.2 Definition of Done (рекомендуемые критерии)

– Код не содержит «Божественных объектов» и опечаток в именовании.  
– UI обеспечивает стабильные 60 FPS на полях 50х50.  
– Ошибки загрузки данных всегда выводятся пользователю.

### 3.3 Корректировка плана разработки

– **Текущая итерация**: рефакторинг движка и переход на Canvas.  
– **Следующая итерация**: внедрение новых топологий и типов мин на базе очищенной архитектуры. Новые фичи разрабатываются только при условии покрытия тестами на граничные значения.
