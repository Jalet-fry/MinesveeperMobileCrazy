## Введение: что и как мы делали

В ходе лабораторной работы мы реализовали полноценное игровое приложение "Сапер" с расширенной логикой: режим зарядов (анти-мины с весом -1), механика аккорда, безопасный старт, рекурсивное открытие пустых областей. Со стороны интерфейса сделали зум и панорамирование, тактильную отдачу, экран статистики с метрикой эффективности.

Мы применили два стиля парного программирования, которые чередовали в зависимости от типа задачи:

| Стиль | Где применяли | Суть |
|-------|---------------|------|
| **«Пинг-понг»** | Разработка ядра (`MinesveeperEngine`) | Один пишет тест, второй пишет код под этот тест. Потом меняемся. |
| **«На равных»** | UI и ViewModel (`GameScreen.kt` + `MinesveeperViewModel.kt`) | Работаем за одним компьютером, обсуждаем каждое решение, код пишет тот, у кого в данный момент клавиатура, но решения принимаем вместе. |

Ниже представлен полный разбор каждого этапа с конкретными примерами кода, комментариями и указанием, кто что делал.

```kotlin
// Файл: MinesveeperEngine.kt
// ЭТОТ КОД НАПИСАЛ ВИТОВТ (Понг, раунд 2)

fun chord(x: Int, y: Int) {
    val cell = cells[y][x]
    
    // Аккорд работает только на открытых клетках с цифрой
    if (!cell.isRevealed || cell.adjacentSum == 0) return
    
    // Считаем флаги вокруг
    var flagsCount = 0
    for (dy in -1..1) {
        for (dx in -1..1) {
            if (dx == 0 && dy == 0) continue
            val nx = x + dx
            val ny = y + dy
            if (isInBounds(nx, ny) && cells[ny][nx].isFlagged) {
                flagsCount++
            }
        }
    }
    
    // Главное условие из теста Жеки:
    // открываем соседей ТОЛЬКО если флагов достаточно
    if (flagsCount == cell.adjacentSum) {
        for (dy in -1..1) {
            for (dx in -1..1) {
                if (dx == 0 && dy == 0) continue
                val nx = x + dx
                val ny = y + dy
                if (isInBounds(nx, ny) && !cells[ny][nx].isFlagged) {
                    revealCell(nx, ny)
                }
            }
        }
    }
}
```

**Комментарий Витовта:** "Я сделал ровно то, что требовал тест: подсчет флагов и проверку условия. Тест Жеки стал зеленым."

// Файл: MinesveeperEngine.kt
// ЭТОТ КОД ПЕРЕПИСАЛ ЖЕКА (Понг, раунд 3)

private fun calculateSum(x: Int, y: Int): Int {
    var result = 0
    
    for (dy in -1..1) {
        for (dx in -1..1) {
            if (dx == 0 && dy == 0) continue
            
            val nx = x + dx
            val ny = y + dy
            
            if (isInBounds(nx, ny)) {
                val cell = cells[ny][nx]
                
                // ВОТ ГЛАВНОЕ ИЗМЕНЕНИЕ:
                if (settings.isChargeMode) {
                    // В режиме зарядов СКЛАДЫВАЕМ значения мин
                    result += cell.mineValue  // +1, -1 и т.д.
                } else {
                    // В обычном режиме просто считаем мины
                    if (cell.isMine) result += 1
                }
            }
        }
    }
    
    return result
}
```

**Комментарий Жеки:** "Раньше я просто проверял `isMine`. Теперь, благодаря тесту Витовта, добавил ветвление. В charge mode работаем с весами, а не с булевыми флагами."

// Файл: MinesveeperEngine.kt
// ЭТОТ КОД НАПИСАЛ ВИТОВТ (Понг, раунд 4)

private fun revealRecursive(x: Int, y: Int) {
    // Проверка границ
    if (!isInBounds(x, y)) return
    
    val cell = cells[y][x]
    
    // Уже открыто или под флагом — выходим
    if (cell.isRevealed || cell.isFlagged) return
    
    // Открываем клетку
    cell.isRevealed = true
    cell.revealedByPlayer = false
    
    // ВАЖНАЯ ОПТИМИЗАЦИЯ (обсудили с Жекой):
    // Не дергаем onStateChanged на каждом шаге рекурсии,
    // чтобы не флудить UI. Вызовем один раз в конце.
    
    // Если клетка пустая — идем дальше
    if (cell.mineValue == 0) {
        for (dy in -1..1) {
            for (dx in -1..1) {
                if (dx == 0 && dy == 0) continue
                revealRecursive(x + dx, y + dy)
            }
        }
    }
    // Если цифра — рекурсия останавливается
}
```

**Комментарий Витовта:** "Ключевой момент — базовый случай рекурсии. Если пусто — идем дальше. Если цифра — останавливаемся. Оптимизацию с колбэком мы обсуждали вместе с Жекой."

## ЧАСТЬ 3. РЕФЛЕКСИЯ (отвечаем на вопросы преподавателя)

### 1. Какую задачу реализовывали?

Мы разработали полноценное игровое приложение "Сапер" со следующими возможностями:
- **Ядро:** генерация поля с безопасной зоной первого клика, механика аккорда, рекурсивное открытие пустых областей, режим зарядов с анти-минами (-1).
- **UI:** зумирование и панорамирование поля (от 0.2x до 5x), тактильная отдача на флаги и события игры, экран статистики с метрикой эффективности.
- **ViewModel:** управление состоянием игры, таймер, счетчик кликов (только за лопату), пауза.

### 2. Какой стиль показался более приемлемым? Почему?

| Стиль | Для чего | Почему |
|-------|----------|--------|
| **«Пинг-понг»** | Ядро игры (MinesveeperEngine) | Потому что сложная логика требует тестирования. Каждый метод появился под конкретный тест, и мы уверены, что ничего не сломается при изменениях. |
| **«На равных»** | UI и ViewModel | Потому что интерфейс — это про договоренности. Мы сразу обсуждали, какие данные нужны на экране, и тут же их реализовывали. Никакой рассинхронизации. |

**Вывод:** Оба стиля хороши, но для разных задач. Пинг-понг дает надежность, на равных — скорость и качество обсуждения.

### 3. Что получилось? Положительные впечатления

1. **Тесты работают.** Все 8 тестов зеленые, мы можем менять код и не бояться сломать старую функциональность.
2. **UI получился удобным.** Зум работает плавно, вибрация приятная, статистика информативная.
3. **Работа в паре ускорила отладку.** Пока один писал код, второй сразу замечал опечатки вроде перепутанных `x` и `y`. Это экономило кучу времени.
4. **Обмен знаниями.** Жека узнал про `LaunchedEffect` и `tick`, Витовт — про жесты и нюансы верстки Compose.

### 4. Что не получилось? Как поправили?

**Проблема:** В начале путались с координатами. Движок хранил массив как `[y][x]`, а методы принимали `(x, y)`. Из-за этого тесты на аккорд падали.

**Решение:** Мы собрались и приняли жесткое правило: **все методы движка и UI принимают параметры в порядке (x, y)**. Записали это правило и следовали ему до конца работы. Больше проблем не было.

### 5. Будете ли использовать ПП для других задач? Каких?

**Да, обязательно.** Парное программирование — это не просто написание кода, а постоянный code review и обмен опытом.

Где пригодится:
- **Сложные алгоритмы** (как в этой лабе) — чтобы сразу тестировать.
- **Рефакторинг легаси** — чтобы меньше бояться что-то сломать.
- **Обучение новичков** — чтобы быстро вводить в курс дела.
