# Лабораторная работа №4 на тему: «Парное программирование»

В ходе данной работы мы применили методики парного программирования для реализации ключевых игровых механик. Основной упор был сделан на стиль **«На равных»**, где мы регулярно менялись ролями «Водителя» и «Штурмана».

---

## 1. План распределения задач (Стиль «На равных»)

Мы разделили разработку на 4 этапа, чередуя ответственность за логику (Backend) и интерфейс (UI).

### Задача 1: Механика «Аккорда» (Backend)
*   **Исполнитель (Водитель):** Витовт
*   **Штурман:** Евгений
*   **Что сделано:** Реализован метод `chord(x, y)` в `MinesveeperEngine`. Логика позволяет автоматически открывать соседние ячейки, если вокруг уже расставлено верное количество флагов. Это значительно ускоряет игровой процесс для опытных игроков.

### Задача 2: Интеграция и Haptic Feedback (UI)
*   **Исполнитель (Водитель):** Евгений
*   **Штурман:** Витовт
*   **Что сделано:** Внедрен вызов `chord` в `MinesveeperViewModel` при повторном клике на ячейку. Добавлен виброотклик (Haptic Feedback) через `LocalHapticFeedback` при установке флага и взрыве, что улучшило тактильные ощущения от игры.

### Задача 3: Алгоритм «Безопасного старта» (Backend)
*   **Исполнитель (Водитель):** Евгений
*   **Штурман:** Витовт
*   **Что сделано:** Переработана логика генерации мин. Теперь при первом клике гарантированно очищается зона 3x3 вокруг курсора, исключая ситуацию, когда игрок проигрывает на первом или втором ходу из-за неудачной генерации.

### Задача 4: Экран статистики и GameOver (UI)
*   **Исполнитель (Водитель):** Витовт
*   **Штурман:** Евгений
*   **Что сделано:** Разработано модальное окно завершения игры. Оно отображает время прохождения, количество сделанных кликов и тип финиша (победа/поражение). Проведена полировка UI-компонентов.

## 2. Применение стиля «Пинг-понг»

Для отладки движка мы использовали стиль «Пинг-понг» при написании Unit-тестов:
1.  **Пинг (Витовт):** Написал тест на некорректный «Аккорд» (когда флагов меньше, чем нужно).
2.  **Понг (Евгений):** Исправил проверку условий в `chord()`, чтобы метод не срабатывал преждевременно.
3.  **Пинг (Евгений):** Написал тест на «Безопасный старт» для полей 50x50.
4.  **Понг (Витовт):** Оптимизировал цикл генерации мин, чтобы избежать зависаний при высокой плотности.

## 3. Впечатления и рефлексия (Ответы на вопросы)

1.  **Какую задачу реализовывали?**
    Реализовали комплексную систему «Аккорда», безопасную генерацию поля и систему статистики в конце игры.
2.  **Какой стиль показался более приемлемым? Почему?**
    **«На равных».** Поскольку мы оба имеем опыт разработки, нам было комфортно дополнять идеи друг друга. Штурман часто замечал опечатки в индексах массивов (например, `x/y` swap), что экономило время на дебаге.
3.  **Что получилось? Положительные впечатления.**
    Код стал чище, а механика «Аккорда» работает стабильно. Работа в паре помогла не «замылить» глаз при верстке интерфейса.
4.  **Что не получилось? Как можно это поправить?**
    Иногда возникали споры о названиях переменных. Решили это использованием стандартного Code Style проекта перед началом работы.
5.  **Будете ли использовать ПП для других задач? Каких?**
    Да, для реализации сетевого режима (мультиплеера), так как там критически важна синхронизация состояний и двойной контроль логики.
